# Homepage Narrative Redesign and UX Behavior Specification for Precision Farming Platform

This document defines the implementation-ready narrative and interaction model for rebuilding the website around a continuous precision-farming implementation story. The goal is to make the homepage read like one coherent business presentation of the company’s implementation system, where each section naturally deepens trust and understanding without feeling like isolated landing blocks.

The homepage begins with a positioning hero that immediately sets strategic context for B2B agriculture managers, then moves into a clear statement of the market problem, then transitions into the company approach and solution architecture, then explains implementation mechanics, then validates with implementation cases, then quantifies economic effect, then proves organizational expertise, then invites the user into a deeper quiz-audit flow, and finally closes with a confident conversion-oriented CTA. The content does not use stage labels and does not introduce artificial numbering mechanics. Instead, the continuity is achieved through narrative bridging microcopy, visual rhythm, and subtle motion that directs attention forward.

The hero section must return to machinery-in-field imagery and explicitly avoid produce close-ups. The visual treatment uses a readability overlay that starts transparent enough at the top and becomes denser toward the bottom with a practical range around rgba(0,0,0,0.35) to rgba(0,0,0,0.7), preserving image quality while ensuring text contrast. The headline speaks to operational control and economic predictability, and the primary CTA should be semantically aligned with the audit path, not with product browsing. A suitable Russian headline can be written as «Система внедрения точного земледелия, которая переводит технологию в управляемую экономику хозяйства», with supporting text that bridges into the next section by naming hidden losses and control gaps.

The market problem section must explain why even advanced farms lose margin in routine operations, describing where losses emerge in sowing, fertilization, spraying, and execution control. The microcopy at the end of this section should transition from diagnosis to method, for example «Чтобы сократить потери, важно не добавлять отдельные устройства, а выстроить целостный контур внедрения». The following approach section then introduces the company system as an implementation architecture rather than a device assortment, clarifying data flow, hardware integration, field execution governance, and KPI verification in one operating loop.

The implementation mechanics section must describe operational reality in plain business language: how diagnosis is conducted, how configuration is selected, how installation and training are organized, how service and KPI control continue through the season. It should avoid rigid phase badges on homepage while still presenting sequence through paragraph continuity and visual timeline accents. The bridge into cases should frame proof as operational evidence, for example «Эта модель ценна только тогда, когда подтверждается в реальных хозяйствах с разными условиями». The cases block on homepage then presents exactly three case cards, each with one concise teaser, one key numeric effect, and a Read case action.

The economic effect section on homepage must remain conceptual and strategic and must not include calculator widgets, ROI forms, or input controls. It should explain what categories of savings are usually unlocked and how decision-makers use economic modeling before procurement. The closing line of this section should naturally push to credibility, for example «Экономика становится устойчивой только при наличии команды, которая отвечает за внедрение и сопровождение». The expertise section then positions the company not as a reseller but as an implementation integrator, with concise proof points about team capability, service footprint, and governance discipline.

Near the end of the homepage, the quiz-audit module appears as the final discovery step. It must feel like a continuation of strategic conversation, not a detached lead form. Before the first question, a short preface screen should state «Есть потенциал оптимизации затрат и повышения управляемости операций. Ответьте на несколько вопросов, чтобы получить аудит точности хозяйства». The final CTA text must be exactly “Get a precision audit for the farm”, with Russian UI equivalent «Получить аудит точности хозяйства». The final CTA section at page end should restate accountability and next action in one clear sentence and one primary action.

The header behavior must be rebuilt to remove duplication and ambiguity. Both logo and Home menu item must lead to homepage. The menu includes Home, About, Catalog, Contacts, and the CTA button Savings Calculation. It remains sticky, shrinks smoothly on scroll, and applies a subtle blur and shadow state after scroll threshold, keeping motion restrained and corporate. The mobile header must preserve readability and touch comfort at 375px with a burger interaction that does not block scroll context.

The calculator page logic must enforce relevance through conditional display. When Operation Type is not Fertilizers, Fertilizer Type and Application Rate must be hidden, must not be required, and must not create layout jump artifacts. When Operation Type is Fertilizers but Fertilizer Type is not yet selected, Application Rate remains hidden and non-required. Only when Fertilizer Type is selected does Application Rate appear and become required. The transition should be animated with mild height/fade easing to avoid visual snapping, while preserving validation integrity and keyboard flow.

The quiz logic must be progressive and operation-aware. The question tree starts with farm profile and operation selection, then branches into relevant follow-ups. If the user selects Sowing, fertilizer type and application rate questions must be skipped entirely. For other operations, only context-appropriate follow-ups appear. Progress bar updates by logical step count after branching, not by static total, so completion percentage remains truthful. Back navigation must preserve previously entered values and keep branch consistency when operation changes.

Cases synchronization must be driven from a single shared data source so homepage and cases page cannot diverge. A practical implementation approach is to store case objects in one JSON-like source and render both pages from the same array. Homepage renderer takes exactly three featured entries from that source, while cases page renders all available entries but always includes those same three. Because the same source controls title, teaser, KPI metric, and slug, numerical mismatches are eliminated.

Site-wide visual cleanup requires harmonized heading scales, normalized line-height, corrected wrapping behavior, and balanced paddings around cards and text clusters. Long paragraphs should be split into shorter semantic blocks to avoid dense walls of text. Links must always be visibly interactive either as button-like controls or as explicit underlined text links with clear hover feedback. Animation language stays subtle with reveal-on-scroll, soft card lift, and restrained hover effects that support narrative flow instead of competing with content.

The mobile experience must keep the same narrative completeness without cutting meaning. At 375px the hero remains readable with preserved contrast, cards stack to one column, case cards become vertically scannable, and the quiz remains thumb-friendly with clear next/back controls and stable progress behavior. Sticky CTA treatment must not obstruct form actions or input fields.

The minimal JavaScript implementation model should include a layout initializer that mounts shared header/footer and header scroll state, a section observer that applies reveal classes once per block, a form controller for AJAX submission with Formspree success/error states, a calculator controller with conditional required attributes tied to operation and fertilizer selection, a quiz controller with branch-aware step registry and dynamic progress calculation, and a case data module consumed by both homepage and cases page renderers. The same form infrastructure should ensure endpoint-driven submission and uniform validation handling across contact, product inquiry, and quiz/audit interactions.

The acceptance criteria are as follows. The homepage must read as one continuous implementation narrative and must not contain any stage labels or numbered stage framing. The homepage must include the full company story in the required sequence from Hero through Final CTA, and it must exclude all calculator widgets and calculator forms while keeping a clear Savings Calculation path in header navigation. The header must include Home, About, Catalog, Contacts, and Savings Calculation with smooth sticky shrink behavior and clean mobile operation. The calculator page must enforce dynamic conditional field visibility and validation exactly according to operation and fertilizer selection logic. The quiz must sit near the end of the homepage, include branch-aware conditional questions, display truthful progress, and end with the CTA Get a precision audit for the farm. Homepage cases must show exactly three entries and remain synchronized with the cases page via one shared source of truth. The entire experience must maintain readable typography, consistent spacing, subtle motion, and full mobile usability at 375px.
